# Manufacturing-App Database Schema Documentation

This folder contains the new Supabase/Postgres schema for the current Manufacturing-App structure.
The backend stays Django API-only. Supabase/Postgres is the source of truth for data.

Migration order:

1. `000_drop_legacy_schema.sql`
2. `001_core_tables.sql`
3. `002_inventory_traceability.sql`
4. `003_product_formula.sql`
5. `004_mixing.sql`
6. `005_njp.sql`
7. `006_assembly.sql`
8. `007_reporting_views.sql`
9. `008_grants.sql`
10. `009_assembly_labels.sql`

Important: `000_drop_legacy_schema.sql` is destructive. It removes old tables, views, relationships, and helper functions. Run it only after backing up the database.

## Main Design

The database follows the actual manufacturing flow:

```text
brands
products
raw_material_categories
raw_materials
inventory_items
inventory_lots
inventory_balances
inventory_movements

products
  -> product_formula_items
      -> raw_materials

products
  -> mixings
      -> mixing_brands
      -> mixing_ingredients
      -> mixing_sessions
      -> output mixed powder inventory lot
          -> njp_runs
              -> njp_load_checks
              -> njp_sessions
              -> output capsule inventory lot
                  -> assemblies
                      -> assembly_brands
                      -> assembly_sessions
                      -> packaging bottle inventory consumption
                      -> assembly_brand_lots
                          -> finished goods inventory lots
```

There is no central `batches` table now. A batch is completed when Assembly produces brand lot codes in `assembly_brand_lots`. This matches the current business rule: Mixing creates powder, NJP creates capsules, Assembly creates final finished goods/batch codes.

No default `Other` raw material category is inserted. If a raw material has no category, `category_id` can be `null`.

## Data Type Choices

| Data Type | Used For | Why It Is Used |
|---|---|---|
| `uuid` | Primary keys and foreign keys | Stable globally unique IDs. Safe for Supabase/API usage and avoids sequence guessing. |
| `text` | Names, codes, remarks, statuses, user-entered labels | Flexible for business text and codes like `MIX-0001`, `NJP-0001`, `786001`, `R1`, `Box 1`. |
| `numeric(18, 6)` | Kg, mg, prices, quantities, percentages | Exact decimal precision. Better than float for inventory, pricing, formula, and manufacturing calculations. |
| `integer` | Counts and small whole-number values | Used where fractional values should not exist, such as bottles made and capsules per bottle. |
| `bigint generated by default as identity` | Internal auto numbers for Mixing, NJP, Assembly | Gives a stable sequence for generating readable codes. |
| `boolean` | Active/inactive flags and primary brand flags | Simple true/false logic for filtering and display. |
| `date` | Manufacturing, expiry, session, received dates | Stores calendar dates without timezone confusion. |
| `time` | Daily start/end time | Stores the time of day separately from date for multi-day stage logs. |
| `timestamptz` | Created/updated timestamps and check time | Timezone-aware audit fields for real production records. |
| `jsonb` | Metadata and record snapshots | Keeps backwards-compatible or extra UI/API fields without changing the schema each time. |

## Key Types Used

| Key Type | Where Used | Benefit |
|---|---|---|
| Primary key | Most tables use `id uuid primary key`; extension tables use `inventory_item_id` as PK | Gives one stable identity per record. |
| Foreign key | Links entities such as product -> mixing, mixing -> NJP, NJP -> assembly | Enforces real relationships and prevents orphan records. |
| Unique index | Codes, brand prefixes, item lot pairs, formula rows | Prevents duplicate business records. |
| Partial unique index | Optional codes like product code, NPN, item code | Allows blanks/nulls but prevents duplicate real values. |
| Check constraint | Status lists, allowed product types, positive quantities, bottle rules | Keeps invalid business data out of the database. |
| Normal index | Search/filter fields and foreign-key lookups | Speeds up API list pages and reports. |
| Trigger | `set_updated_at`, code generation | Keeps audit fields and readable codes consistent. |

## 000_drop_legacy_schema.sql

Type: destructive reset migration.

Purpose:

- Removes old schema objects before applying the new structure.
- Drops both the new schema objects if they already exist and the old legacy objects.
- Removes old batch-related tables because the new system does not use a central Batch concept.

Objects dropped:

- New schema views/tables/functions if they already exist.
- Old `batches`, stage reports, finished goods, labels, bottles/lids, HR, finance, procurement, company settings, and old helper functions.

Why it exists:

- It avoids conflicts when replacing the old project structure.
- It gives a clean database for the new manufacturing traceability model.

### `inventory_balances`

Type: current stock table.

Purpose: Stores the current quantity on hand per item/lot/location.

Columns:

| Column | Data Type | Key/Rule | Why |
|---|---|---|---|
| `id` | `uuid` | Primary key | Stable balance row. |
| `inventory_item_id` | `uuid` | FK to inventory_items | Item being counted. |

Allowed movement types:

- `receive`
- `consume`
- `produce`
- `adjust`
- `transfer_in`
- `transfer_out`
- `delete_reversal`

### Function: `apply_inventory_movement`

Type: database function/RPC.

Purpose:

- Updates `inventory_balances`.
- Inserts a row in `inventory_movements`.
- Blocks negative inventory.
- Uses `idempotency_key` to avoid duplicate movement from retrying an API call.

Benefit:

- Inventory rules are enforced close to the data, not only in frontend/backend code.

## 004_mixing.sql

### `mixings`

Type: manufacturing transaction table.

Purpose: Stores each powder/mixing run.

Columns:

| Column | Data Type | Key/Rule | Why |
|---|---|---|---|
| `id` | `uuid` | Primary key | Stable mixing identity. |
| `mixing_number` | `bigint identity` | Internal sequence | Used to generate `MIX-0001`. |
| `mixing_code` | `text` | Unique, auto-generated if blank | Human-readable mixing code. |
| `product_id` | `uuid` | FK to products, restrict delete | Mixing is for one product. |
| `location_id` | `uuid` | FK to locations, set null | Structured location. |
| `location_text` | `text` | Optional | Free-text location like `R1`. |
| `total_kg_in_mixing` | `numeric(18,6)` | Must be positive | Final desired powder quantity. |
| `existing_mixed_powder_lot_id` | `uuid` | FK to inventory_lots | Old powder used in new mixing. |
| `existing_mixed_powder_used_kg` | `numeric(18,6)` | Non-negative | Quantity reused from old powder. |
| `fresh_mixing_required_kg` | `numeric(18,6)` | Non-negative | New formula powder required. |
| `calculated_fresh_raw_materials_total_kg` | `numeric(18,6)` | Default `0` | Sum of calculated raw material kg. |
| `total_mixed_qty_kg` | `numeric(18,6)` | Must equal total kg | Output powder qty. |
| `output_inventory_item_id` | `uuid` | FK to inventory_items | Produced powder inventory item. |
| `output_inventory_lot_id` | `uuid` | FK to inventory_lots | Produced powder lot. |
| `status` | `text` | Check list | Run status. |
| `remarks` | `text` | Optional | User remarks. |
| `change_reason` | `text` | Optional | Why formula was modified. |
| `version` | `integer` | Default `1` | Edit/version tracking. |
| `record_snapshot` | `jsonb` | Default `{}` | Full API/UI record snapshot. |
| `created_at` | `timestamptz` | Default `now()` | Audit timestamp. |
| `updated_at` | `timestamptz` | Trigger maintained | Audit timestamp. |

Allowed statuses:

- `draft`
- `underprocess`
- `completed`
- `cancelled`

Important calculation rule:

```text
fresh_mixing_required_kg = total_kg_in_mixing - existing_mixed_powder_used_kg
existing_mixed_powder_used_kg < total_kg_in_mixing
total_mixed_qty_kg = total_kg_in_mixing
```

Benefit:

- Reused powder reduces only the fresh raw material calculation.
- The finished output still equals the full requested mixing quantity.

| `updated_at` | `timestamptz` | Trigger maintained | Audit timestamp. |

Allowed statuses:

- `underprocess`
- `completed`

Bottle validation:

- `bottle_type = 'capsule'` requires `bottle_size in (200, 250, 300)`.
- `bottle_type = 'jar'` requires `bottle_size is null`.

Business rule:

- Assembly deducts the matching bottle inventory from `packaging_items` and inventory lots.
- If enough matching bottles are not available, the backend/database flow blocks the save.
- `label_id`/`label_lot_id`/`total_labels_used` (added in `009_assembly_labels.sql`) track label
  inventory consumption. `total_labels_used` always equals `total_bottles_made` (one label per bottle)
  and is deducted from label inventory the same way bottle/packaging inventory is deducted.
- Rejected capsules are handled in NJP (`njp_runs.rejected_capsules_qty`), not in Assembly. Assembly's
  `capsules_received_qty` simply consumes whatever net/available capsule count NJP produced.

## Relationship Summary

### Product Formula

```text
products.id
  -> product_formula_items.product_id

raw_materials.inventory_item_id
  -> product_formula_items.raw_material_id
```

Benefit:

- Formula rows are reusable for pricing and mixing calculation.

### Inventory Model

```text
inventory_items.id
  -> inventory_lots.inventory_item_id
  -> inventory_balances.inventory_item_id / inventory_lot_id
  -> inventory_movements.inventory_item_id / inventory_lot_id
```

Benefit:

- Current balance and full movement history are both available.

### Mixing

```text
products.id
  -> mixings.product_id

mixings.id
  -> mixing_brands.mixing_id
  -> mixing_ingredients.mixing_id
  -> mixing_sessions.mixing_id

mixings.output_inventory_lot_id
  -> inventory_lots.id
```

Benefit:

- A mixing can have multiple brands and creates reusable mixed powder inventory.

### NJP

```text
mixings.id
  -> njp_runs.mixing_id

njp_runs.id
  -> njp_load_checks.njp_id
  -> njp_sessions.njp_id

njp_runs.output_capsule_lot_id
  -> inventory_lots.id
```

Benefit:

- NJP consumes available powder and creates available capsule bulk.

### Assembly and Finished Goods

```text
njp_runs.id
  -> assemblies.njp_id

assemblies.id
  -> assembly_brands.assembly_id
  -> assembly_sessions.assembly_id
  -> assembly_brand_lots.assembly_id

assembly_brand_lots.finished_good_lot_id
  -> inventory_lots.id
```

Benefit:

- Assembly consumes capsules and bottles.
- Final finished goods are brand-specific through `assembly_brand_lots`.
- Multi-brand batch codes are represented cleanly without putting many brand-specific columns into the main assembly table.

## Why This Structure Is Better

1. Traceability is complete.
   Raw materials go into Mixing, Mixing goes into NJP, NJP goes into Assembly, Assembly creates Finished Goods.

2. Inventory is controlled by ledger.
   Every receive, consume, produce, adjustment, and reversal can be tracked.

3. Reports are not duplicated.
   Views generate reports from real data.

4. Multi-brand manufacturing is supported.
   Mixing and Assembly can attach multiple brands without duplicating the manufacturing record.

5. Bottle validation is enforced.
   Capsule bottles need size `200`, `250`, or `300`; Jar/Lid does not use capsule size.

6. The schema is stable but flexible.
   Important business columns are normalized. `metadata` and `record_snapshot` preserve compatibility for evolving UI/API fields.

7. The backend can move away from JSON safely.
   The current JSON relationships now have matching database tables and foreign keys.
